A major platform migration at a global biotechnology company required moving data from legacy inventory and registry systems to a new vendor platform. Numerous internal applications still depended on the legacy APIs, making compatibility essential throughout the transition.

The engineering team was building a proxy layer to translate requests and responses between the new platform and existing applications. When I returned from parental leave, development was already underway.

I noticed two significant risks: the migration backlog lacked a documented basis for determining which endpoints were still necessary, and the implementation relied heavily on unit tests without sufficient integration testing to establish behavioral compatibility.

Rather than simply continue implementing the backlog, I separated the problem into two questions:

* Should this endpoint be migrated at all?
* If so, how do we know its replacement preserves the required behavior?

Answering only the second question would have meant spending engineering effort validating interfaces that might no longer serve a purpose.

## Challenge the migration scope with actual usage evidence

The existing migration plan included endpoints that were obsolete, unused, or no longer relevant following changes to the underlying data models.

I built Kibana and CloudWatch dashboards to investigate endpoint usage over the preceding year, including which applications were making requests. I also developed a reusable agent skill that allowed engineers to investigate individual endpoints and retrieve supporting traffic evidence.

However, traffic data alone couldn't determine whether an endpoint should be preserved. The organization's continued support commitments also mattered.

I worked with technical leads, Product, and engineering leadership to establish a shared decision criterion: endpoints with no traffic from applications still receiving support did not need to be carried forward into the new proxy implementation.

Applying that criterion identified 37+ unnecessary endpoint migrations, which were subsequently removed from the development backlog.

Based on historical ticket completion times, this represented a substantial amount of avoided development work. More importantly, it prevented the organization from introducing additional interfaces that would require maintenance and could mislead future engineers into believing obsolete behaviors remained necessary.

The investigation also changed our planning process. Engineers began verifying endpoint usage before committing additional migration work, rather than treating the inherited backlog as authoritative.

## Establish behavioral correctness against the real system

Reducing the migration scope addressed unnecessary work, but it didn't resolve another critical question: whether the endpoints we did migrate behaved correctly.

With management approval, I developed an initial shadow-diff MVP in approximately three weeks using agentic engineering tools.

The tool compared response behavior between legacy and replacement implementations, exposing discrepancies that existing unit tests could miss.

During early development, I interviewed engineers to understand where they believed the authoritative API contracts lived. The team identified a typed legacy API client, which led me to add static contract comparison functionality.

That decision turned out to be a mistake.

Further investigation revealed that the typed client did not accurately represent all of the legacy system's behavior. Although the static comparison feature worked technically, its results were not a trustworthy measure of compatibility.

**I had built functionality around an abstraction before validating whether that abstraction was authoritative.**

Rather than continue expanding that approach, I focused on direct behavioral comparison.

The resulting analysis examined more than 200 endpoints and exposed widespread contract discrepancies, missing negative-path parity, and previously overlooked behavioral branches.

To investigate those branches more systematically, I developed a separate coding-agent workflow that examined the actual JavaScript implementation of the legacy inventory and registry systems.

Instead of inferring behavior from potentially inaccurate client definitions, the agent analyzed the implementation to identify expected contracts and conditional behavior.

That investigation identified 75 missing behavioral branches in the replacement endpoints.

## Turn the findings into a repeatable engineering process

Finding discrepancies was valuable, but the larger opportunity was to make behavioral verification part of normal engineering delivery.

Shadow-diff testing was integrated into CI, providing a repeatable way to check compatibility as implementation work progressed.

Engineering leadership prioritized corrective work for the identified behavioral discrepancies, excluding negative-path parity issues from that initial prioritization.

I then used a separate custom agentic build harness to address approximately 95% of the resulting corrective bug tickets.

This was distinct from the 37+ endpoint migrations removed from the backlog. Those migrations represented work we avoided; the corrective tickets addressed deficiencies in implementations that still needed to exist.

Together, the changes established two complementary engineering practices:

* Validate necessity before implementation. Use observed behavior and support requirements to determine which interfaces warrant continued investment.
* Validate correctness against actual behavior. Compare replacement implementations with the legacy system and retain regression checks throughout delivery.

The result was a smaller migration scope, substantially better visibility into compatibility risks, and a more repeatable approach to validating the work that remained.

## What I learned about technical and organizational judgment

The first lesson was about the importance of validating assumptions before building automation around them.

Typed interfaces and documented contracts are useful abstractions, but they are not necessarily authoritative descriptions of actual system behavior. My initial static comparison feature reinforced that distinction.

If I approached the project again, I would establish the behavioral source of truth earlier and keep the first MVP more tightly focused on directly validating it.

The second lesson concerned how technical discoveries are introduced to an engineering team.

The findings challenged significant work that colleagues had already completed. Although the investigation was respected and the resulting corrective work was prioritized, I recognized that presenting a largely completed analysis could leave engineers feeling that their contributions were being judged rather than that they were participating in uncovering a shared problem.

I would make that discovery process more collaborative, involving engineers earlier in investigating discrepancies and establishing the evidence together.

> Engineering leadership isn't only about reaching the right technical conclusion. It's also about creating the shared understanding necessary for people to act on it.

Ultimately, this experience reinforced a principle I've carried into subsequent engineering systems: validate the assumptions behind planned work, establish trustworthy evidence for correctness, and make those practices repeatable rather than dependent on individual judgment.
